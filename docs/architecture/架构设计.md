# 五金商贸网站 · MVP 架构设计

> 版本 v1.0 ｜ 2026-11-07 ｜ 依据：`docs/MVP需求初稿.md`（已确认基准需求）

## 0. 文档目的与范围

本文确定 MVP 的技术选型、系统架构、关键流程、数据模型、权限模型、部署方案与演进方向，作为前后端、数据库、运维落地的统一依据。MVP 原则：**单体优先、前后端分离、最少依赖、闭环优先**。

---

## 1. 技术选型

| 层 | 选型 | 版本建议 | 结论理由 |
| --- | --- | --- | --- |
| 前端框架 | Vue 3 + TypeScript + Vite | Vue 3.5 / Vite 6 | 中文生态成熟、上手快、适合与后台并行开发；TS 提升可维护性 |
| 前端 UI | Element Plus（前台+后台统一） | 2.x | 组件齐全，后台 CRUD 与前台商城均可覆盖，减少双框架学习成本 |
| 前端状态/路由 | Pinia + Vue Router | 4.x | Vue 官方推荐，简单 |
| 后端框架 | Python + FastAPI | Python 3.13 / FastAPI 0.115+ | 契合已有 PyCharm + Python 环境；异步高性能、自动 OpenAPI 文档、类型校验，MVP 迭代快 |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic | 2.0 / 1.13 | 成熟稳定，事务与迁移能力满足支付场景 |
| 校验 | Pydantic v2 | 2.x | FastAPI 原生集成，请求/响应强校验 |
| 数据库 | PostgreSQL 16 | 16 | 强一致性与严格约束、类型系统丰富、云厂商托管成熟、契合强校验风格 |
| 缓存 | 不引入（MVP） | — | 用 JWT 无状态 + 数据库唯一约束/事务满足需求；Redis 列后续演进 |
| 部署 | Docker Compose 单机（Nginx + API + PostgreSQL） | — | 单体最小部署面，环境可复现，易迁移 |
| 反向代理/TLS | Nginx | — | 静态资源 + TLS 终止 + 反代；支付回调需公网域名 + HTTPS |

### 1.1 选型理由（关键权衡）

- **为何前后端分离而非服务端模板**：前台买家端、后台管理端是两个独立交互域，分离后前端/后端可并行开发，且前后端都已有成熟脚手架（Vue + FastAPI），整体开发速度优于服务端模板混排。
- **为何 FastAPI 而非 Node/Java**：开发机为 Windows 11 + PyCharm、用户已有 Python 环境；FastAPI 类型提示 + Pydantic 在「订单/支付」这种强校验场景错误率低；单体项目无需 Spring 的重量级工程结构。
- **为何 PostgreSQL 而非 MySQL**：订单/支付场景对数据一致性要求高，PostgreSQL 的 MVCC 与更严谨的事务隔离、完整的外键/CHECK 约束能力可减少应用层兜底逻辑；严格类型系统契合 FastAPI + Pydantic 的强校验风格；JSONB 与扩展生态为后续演进留空间；云厂商（阿里云/腾讯云 RDS PostgreSQL）托管同样成熟，运维成本不高于 MySQL。
- **为何不引入 Redis**：MVP 无高并发秒杀，购物车与订单状态用 PostgreSQL 即可；支付回调幂等靠「支付流水唯一键 + 订单状态机 + 数据库事务」保证，不需要分布式锁。Redis 是明确的后续演进项而非本期负担。

## 2. 系统架构

### 2.1 总体形态

**单体后端 + 双前端 SPA**。后端为 FastAPI 单体应用，内部按模块分层；前端为两个独立 SPA（前台买家端、后台管理端），均通过 REST/JSON 访问同一后端 API。

### 2.2 后端分层与模块

```
前端（shop-web 买家端 / admin-web 管理端）
        │  HTTPS / REST JSON
        ▼
┌────────────────────── 表现层（API Router）──────────────────────┐
│  买家 API    │  管理 API（JWT + role=admin 鉴权）  │  支付回调 API  │
├────────────────────── 应用服务层（Service）──────────────────────┤
│ auth 认证   │ catalog 商品/分类/价格  │ cart 购物车              │
│ order 订单  │ payment 支付            │ member 会员/地址/等级     │
├────────────────────── 领域层（Domain 规则）──────────────────────┤
│  分级价格取值   │  订单状态机   │  库存扣减/回补   │  支付幂等验签  │
├────────────────────── 数据访问层（Repository / ORM）─────────────┤
│                        SQLAlchemy 2.0 模型                        │
└───────────────────────────────────────────────────────────────────┘
        │
        ▼
   PostgreSQL 16       微信/支付宝支付网关           本地磁盘/对象存储(商品图)
```

分层职责边界：

- **表现层**：参数校验、鉴权、路由分发、响应封装，不写业务规则。
- **应用服务层**：用例编排（如下单 = 校验库存 + 锁定价格 + 创建订单 + 创建支付单）。
- **领域层**：纯业务规则，独立可测：分级价格取值、订单状态机（只允许合法流转）、库存增减规则。
- **数据访问层**：仅持久化与查询，不掺业务判断。

### 2.3 前端结构

- `shop-web`（前台买家端）：首页/分类/商品列表/详情/搜索、购物车、结算下单、订单中心、登录注册、地址管理。PC 优先、响应式适配移动。
- `admin-web`（后台管理端）：商品/分类/价格/客户/订单/支付流水管理。桌面为主，复用 Element Plus 后台布局。

两个 SPA 共享同一套 REST API，通过 JWT 中的 `role` 区分买家/管理员。

## 3. 关键业务流程

### 3.1 下单支付流程（时序要点）

1. 买家登录后浏览商品，**按等级实时取价**展示。
2. 加购：购物车存 `product_id + 数量`，价格不在购物车落库。
3. 结算：选地址 → 后端校验库存 → **按等级重新计算单价与总额** → 生成订单（状态=待支付）+ 支付单。
4. 创建支付：后端调支付网关（微信 Native/JSAPI 或支付宝）生成预支付单，返回二维码/支付参数。
5. 买家完成支付 → 支付网关**异步回调** → 后端验签 + 幂等 → 订单转「已支付」、扣减库存、记录支付流水 → 返回成功应答。
6. 商家后台发货 → 「已发货」；买家确认收货 → 「已完成」。
7. 待支付订单可取消（回补占用库存）；支付超时自动取消为 P1 可选。

### 3.2 分级价格取值逻辑

- `product.price` 为零售价（基础价），游客与未单独设置等级的会员均取零售价。
- `product_price(product_id, level)` 按「商品 × 等级」显式设置价格；登录会员优先取本人等级价格，未设置则回退零售价。
- 后台「按等级批量折扣」作为快捷操作，**即时展开写入 `product_price` 冗余落库**，下单与展示只读 `product_price`，避免运行时折扣计算。

### 3.3 订单状态机

```
待支付 PENDING_PAYMENT
   ├── 买家取消 / 超时(可选) ──→ 已取消 CANCELLED（回补库存）
   └── 支付成功回调 ───────────→ 已支付 PAID（扣减库存）
已支付 PAID
   └── 商家发货 ───────────────→ 已发货 SHIPPED
已发货 SHIPPED
   └── 买家确认收货 ───────────→ 已完成 COMPLETED
```

状态流转仅在领域层状态机内进行，非法流转（如已发货 → 待支付）直接拒绝。MVP 不做退款，支付失败保持待支付。

## 4. 数据模型（核心实体）

> 完整 ER 图见 `docs/architecture/er-diagram.drawio`。下表为实体与关系说明。

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `user` | 用户（买家/管理员，role 区分） | id, username, password_hash, role, phone |
| `customer_level` | 客户等级字典 | code(零售/批发/VIP), name, sort |
| `member_profile` | 会员资料（关联等级） | user_id(FK), level_code(FK), real_name |
| `category` | 商品分类（多级自引用） | id, parent_id(自引用), name, sort |
| `product` | 商品 SPU（单品+规格文本） | id, category_id, name, model, description, retail_price, stock, status, main_image |
| `product_image` | 商品多图 | id, product_id(FK), url, sort |
| `product_spec` | 规格属性文本（不单独计价） | id, product_id(FK), spec_name, spec_value |
| `product_price` | 分级价格（商品×等级） | id, product_id(FK), level_code(FK), price；唯一(product_id, level_code) |
| `cart_item` | 购物车项 | id, user_id(FK), product_id(FK), quantity |
| `address` | 收货地址 | id, user_id(FK), receiver, phone, region, detail |
| `order` | 订单主表 | id, order_no(唯一), user_id, status, product_amount, freight_amount, total_amount, address 快照, created_at |
| `order_item` | 订单项（价格快照） | id, order_id(FK), product_id, product_name 快照, price, quantity, subtotal |
| `payment` | 支付流水 | id, order_id(FK), channel(wechat/alipay), trade_no(第三方), amount, status, paid_at；唯一(order_id, channel) 保证幂等 |

关系要点：

- `user` 1—1 `member_profile` N—1 `customer_level`；`user` 1—N `cart_item` / `address` / `order`。
- `category` 自引用（parent_id）构成多级树。
- `product` 1—N `product_image` / `product_spec` / `product_price`；`product_price` N—1 `customer_level`。
- `order` 1—N `order_item` N—1 `product`（订单项保留名称/单价快照，防止商品改价影响历史订单）。
- `order` 1—N `payment`（一笔订单可有多次支付尝试，唯一约束防重复回调）。

## 5. 权限模型

| 角色 | 权限 | 实现 |
| --- | --- | --- |
| 游客 | 浏览商品/分类、搜索、**查看零售价** | 无 JWT |
| 会员（零售/批发/VIP） | 游客权限 + **按等级看价** + 购物车 + 下单支付 + 订单中心 + 地址/资料管理 | JWT，`role=member` + `level_code` |
| 管理员 | 后台商品/分类/价格/客户/订单/支付流水管理；可前台以零售身份看价 | JWT，`role=admin` |

实现要点：JWT 无状态认证；后端依赖注入做接口级鉴权（买家接口校验 `role=member`，管理接口校验 `role=admin`）；**价格接口按登录态动态返回**——游客返回零售价，会员返回等级价（无等级价回退零售价），管理员后台按等级查看/编辑价格。

## 6. 部署与运维（MVP）

### 6.1 部署拓扑

```
互联网用户 ──HTTPS──▶ Nginx(443, TLS 终止 + 静态资源 + 反代)
                         │
              ┌──────────┴──────────┐
              ▼                      ▼
        shop-web / admin-web     api 容器(FastAPI + uvicorn)
        (静态文件, 由 Nginx 托管)        │
                                        ▼
                              postgres 容器(16, 数据卷持久化)
```

- 单机 Docker Compose：`nginx` + `api` + `postgres` 三容器；`docker-compose.yml` + `.env`（密钥/支付商户号/DB 口令）。
- 主机：腾讯云/阿里云 CVM 或轻量服务器（需公网 IP + 备案域名）。

### 6.2 关键要求

| 项 | 方案 |
| --- | --- |
| HTTPS | Nginx + 云厂商免费证书或 Let's Encrypt；全站强制 HTTPS |
| 支付回调可达性 | 备案域名 + 公网 IP，开放 443；回调路由 `/api/payment/notify/*` 不设登录鉴权（仅验签） |
| 回调幂等 | `payment(order_id, channel)` 唯一约束 + 订单状态机 + 事务，重复回调不重复发货/扣减 |
| 备份 | PostgreSQL 每日 `pg_dump` 定时任务，归档到 OSS/异地；`.env` 与证书备份 |
| 日志 | uvicorn/Nginx 访问日志 + 应用日志按天轮转；支付回调日志单独留存便于对账 |
| 静态资源 | MVP 商品图存本地磁盘卷（Nginx 或 API 静态托管），量级增大后迁对象存储 |

## 7. MVP 技术取舍与后续演进

### 7.1 本期简化（明确不做/简化）

- 单品 + 规格属性文本，不做多规格 SKU 独立计价/分库存。
- 统一运费（可选满额包邮），不做运费模板。
- 固定 3 级客户等级，后台人工指定，不做自动升级。
- 简单库存扣减/回补，不做进销存/多仓。
- 不做优惠券/满减/促销、商品评价、发票、短信邮件通知。
- 不引入 Redis、消息队列、微服务、搜索引擎（搜索用 PostgreSQL LIKE/ILIKE，数据量大再上 ES）。

### 7.2 后续演进方向

| 阶段 | 演进项 | 触发条件 |
| --- | --- | --- |
| 迭代一 | 多规格 SKU（product 拆 product_sku，价格/库存下沉） | 商品多尺寸/材质需独立计价 |
| 迭代一 | 引入 Redis（会话共享、购物车缓存、库存锁、限流） | 流量上升、多实例部署 |
| 迭代二 | 消息队列（支付回调异步化、订单超时取消、通知） | 回调高峰/通知需求 |
| 迭代二 | 优惠券/促销引擎、运费模板 | 运营活动需求 |
| 迭代二 | 商品图迁对象存储（OSS/COS） | 图片量增长 |
| 迭代三 | 搜索升级（Elasticsearch）、统计看板增强 | 商品量/运营需求 |
| 迭代三 | 按模块微服务拆分（用户/商品/订单/支付） | 团队扩大、模块独立迭代需求 |
